# 4-1. 운영체제의 메모리 관리, x86-64 에서의 메모리

운영체제의 가장 핵심적인 업무는 사용자가 원하는 프로그램을 실행시켜 주는 것입니다. 프로그램을 실행하려면 디스크 등에 저장된 실행파일 데이터를 컴퓨터 상의 메모리(RAM)에 적재(Load)해야 합니다.

여러분이 리눅스 터미널에서 `./program` 처럼 어떤 프로그램을 실행해 달라고 입력하면, 셸(Shell)과 커널 내부에서는 다음과 같은 작업들을 순차적으로 진행합니다.

1. **명령어 해석** : 셸은 사용자의 명령어를 읽고, 실행할 파일의 경로 `./program`을 확인합니다.
2. **프로세스 복제** : 셸은 먼저 `fork()` 시스템 호출을 통해 자신과 같은 프로세스를 하나 복제합니다.
3. **실행 요청** : 복제된 자식 프로세스는 커널에 `execve()` 시스템 호출을 합니다. 현재 프로세스를 새로운 프로그램으로 덮어쓰는 요청입니다.
4. **메모리 적재** : 운영체제는 위에서 받은 파일이 올바른 리눅스 실행파일(ELF)인지 확인하고, 프로세스가 사용할 코드, 데이터, 스택, 힙 영역 등의 **논리 메모리 공간**을 만들고 실행파일의 내용을 논리 메모리에 적재합니다.

### 잠깐! '논리 메모리 공간'이 도대체 무엇인가요?

논리 메모리(Logical Memory)는 해킹과 컴퓨터 공학에서 흔히 <b>가상 메모리(Virtual Memory)</b>라고 부르는 개념입니다.

쉽게 말해, **운영체제가 각 프로세스에게 보여주는 가짜 주소값**입니다.

우리가 GDB 등 디버거를 사용하여 확인하는 주소값들은 **사실 컴퓨터의 실제 RAM(물리 메모리)에 적재된 진짜 주소값이 아닙니다!** 운영체제가 각 프로세스마다 만들어 준 가짜 주소일 뿐입니다.

그럼 실제로 프로그램을 실행시키려면, 이 가짜 주소를 실제 하드웨어상의 진짜 주소(물리 주소, Physical Address)로 바꿔 주어야겠죠?

이 역할을 하는 것이 바로 CPU 안에 내장된 <b>MMU (Memory Management Unit, 메모리 관리 유닛)</b>라는 하드웨어입니다. CPU가 가짜 주소를 읽으려 할 때, MMU가 중간에 개입하여 이를 진짜 물리 주소로 빠르게 번역해 줍니다.(번역에 걸리는 시간은 1 나노초($10^{-9}$초)도 되지 않습니다!)

이때 MMU가 번역을 제대로 할 수 있도록, 운영체제는 메모리 어딘가에 **가상 주소와 물리 주소간 대조표**를 만들어 놓습니다. 이 거대한 번역 사전(대조표)을 바로 <b>페이지 테이블(Page Table)</b>이라고 부릅니다.

즉, 사용자가 느끼기에는 코드, 데이터, 스택, 힙이 연속된 공간에 아주 깔끔하게 정리된 것처럼 보이지만...

사실은 커널의 철저한 관리하에 컴퓨터 RAM의 남는 조각들에 파편화되어 저장되어 있습니다. (심지어 RAM이 꽉 차면 일부 데이터는 하드디스크로 쫓겨나기도 합니다!) 사용자 눈에는 커널과 MMU가 만들어 낸 착각을 볼 뿐입니다.

## x86-64 CPU의 진짜 메모리 범위는 어디까지일까?

x86-64 아키텍처는 이름 그대로 64비트 레지스터를 사용합니다. 컴퓨터가 한 번에 64비트의 주소를 처리할 수 있으므로, 이론상 메모리에 할당할 수 있는 주소의 범위는 `0x0000000000000000`부터 `0xffffffffffffffff`까지입니다.

바이트 단위로 환산하면 무려 <b>16EB(엑사바이트, 약 1,670만 TB)</b>에 달하는 천문학적인 공간입니다! 하지만 우리가 사용하는 현대의 64비트 컴퓨터들은 저 많은 주소를 모두 사용하지도 않으며, 굳이 그럴 필요도 없습니다. 왜일까요?

이를 이해하려면 컴퓨터 구조에서 버스(Bus)에 대한 이해와 실제 컴퓨터 칩 제조 과정에 대한 이해가 필요합니다.

> **버스(Bus)가 무엇인가요?**
>
> 컴퓨터에서 버스는 CPU, 메모리, 입출력 장치 등 컴퓨터를 구성하는 부품들이 데이터를 주고받기 위해 사용하는 전기적 선로(회로) 입니다.
>
> 실제로 컴퓨터 칩을 제작할 때, 실리콘 웨이퍼(Wafer)를 깎아 CPU 다이(Die)를 만들고 메인보드 기판을 인쇄한 후 이 선로들이 물리적인 구리선으로 빼곡하게 깔리게 됩니다.
>
> 버스는 종류에 따라 다음과 같이 구분합니다.
> - **데이터(Data) 버스** : 명령어 및 데이터가 이동하는 양방향 통로입니다.
> - **주소(Address) 버스** : 데이터가 도착할 메모리의 위치를 알려주는 단방향 통로입니다.
> - **제어(Control) 버스** : 읽기/쓰기 등 신호를 전달하는 단방향 통로입니다.

처음 AMD가 x86-64(AMD64) 구조를 설계하던 시절, 개인용 컴퓨터의 RAM은 기껏해야 수백 MB에서 1~2 GB 수준이었습니다. 16EB는 미래를 생각하더라도 지나치게 낭비되는 수치였죠.

반도체 공학자들의 입장에서 '64비트 주소 체계를 완벽히 지원한다'는 것은 CPU 기판과 메인보드에 주소를 전달하는 물리적인 구리선(주소 버스)을 무려 64가닥이나 촘촘하게 깔아야 한다는 뜻입니다.(1비트당 신호선 1가닥이 필요합니다.)

이것은 다음과 같은 문제를 발생시킵니다.

1. 어차피 16EB는커녕 1TB의 RAM도 꽂을 일이 없는 시대였습니다. 현재도 가정용 컴퓨터는 16GB/32GB 수준으 RAM으로 충분합니다.
2. 쓰지도 않을 공간을 위해 CPU 다이에 회선들을 구겨 넣는 것은 엄청난 자원 낭비이자 원가 상승의 주범입니다.
3. 게다가 미세한 회선이 늘어날수록 전파 간섭(노이즈)이 심해져서, 차폐선을 깔고 신호 증폭기(리피터)를 수없이 달아야 하는 등 설계도 어려워집니다.

따라서 CPU 제조사들은 제조 과정에서, 레지스터는 64비트를 모두 쓰되 **주소 버스는 48비트(48가닥)까지만 제작하기로 했습니다.** 

48비트만 해도 최대 256TB의 논리 메모리를 지원하므로, 현대 컴퓨터 환경에서도 여전히 차고 넘치는 용량입니다. 신호선 16가닥을 제거했으니 CPU 크기도 줄어들고, 남는 공간에 연산장치(ALU)나 캐시 메모리(L1/L2)를 더 넣어 CPU의 성능을 더 향상시킬 수 있습니다.

**그렇다면 64비트 레지스터에 48비트 주소만 담으면 남는 상위 16비트는 어떻게 처리할까요?**

여기서 사용하는 것이 <b>정형 검사(Canonical Check)</b>입니다. CPU는 48번째 비트(Bit 47)의 값을 확인하고, **남은 상위 16개 비트를 모두 Bit 47과 같은 값으로 설정(부호 확장)을 합니다.**

그 결과, 현대 64비트 운영체제의 논리 주소 공간은 다음과 같이 나뉘어졌습니다.

- `0x0000000000000000` - `0x00007fffffffffff` (Lower Half): 사용자 영역입니다.
- `0x0000800000000000` - `0xffff7fffffffffff` (Non-Canonical Area): 유효하지 않은 영역입니다. CPU가 이 주소에 접근하려 하면 즉시 예외(Fault)를 발생시킵니다.
- `0xffff800000000000` - `0xffffffffffffffff` (Upper Half): 커널 영역입니다.

여러분들이 사용자 영역 시스템 해킹을 할 때, 스택이나 라이브러리 주소가 항상 `0x7fff...`쯤에서 놀고 있던 것, 그리고 우리가 3장까지의 익스플로잇 코드에서 커널 영역의 함수나 가젯을 찾을 때 주소가 죄다 `0xffff...`로 시작했던 것, 기억하시나요? 무심코 지나쳤던 그 주소들의 형태가 사실 반도체 하드웨어 설계의 흔적이랍니다!

커널 입장에서도 이렇게 설계해 두면, 주소의 맨 앞 비트(상위 비트)만 확인해도 사용자/커널 영역 구분을 할 수 있어 보안 검사 속도가 엄청나게 빨라지는 이점까지 챙길 수 있답니다.
