# 6-1. CPU 게이트 : 전 세계를 공포로 몰아넣은 하드웨어 대재앙

여러분은 **하드웨어 자체에도 보안 취약점이 존재할 수 있다는 사실을 알고 계시나요?**

운영체제나 응용 프로그램 같은 소프트웨어에서 취약점이 발견되면 코드를 수정해서 배포(업데이트/패치)를 합니다. 하지만 하드웨어에 설계 결함이 발견된다면 이야기가 다릅니다. **공장에서 이미 찍혀 나온 반도체 칩은 영구히 수리할 수 없기 때문입니다.** 즉, 컴퓨터 시스템에 영원히 고칠 수 없는 '불치병'이 생기는 것과 같습니다.

그런데 여기서 잠깐! **만약 지구상에 존재하는 거의 모든 컴퓨터의 중앙처리장치(CPU)에, 운영체제의 모든 비밀 데이터 정보를 훔쳐볼 수 있는 치명적인 취약점이 무려 20년 동안이나 숨어 있었다면... 믿으시겠습니까?**

전 세계 IT 업계를 발칵 뒤집어 놓았던 충격적인 하드웨어 보안 사태, 일명 <b>'CPU 게이트'</b> - 그 중에서도 현대 운영체제 보안의 근간을 뒤흔들었던 <b>멜트다운(Meltdown, CVE-2017-5754)</b>을 소개합니다. (이 글에서는 핵심 원리만 간단히 다루겠습니다. 전체 사건의 전말과 상세한 기술 문서가 궁금하시다면 [공식 멜트다운 페이지](https://meltdownattack.com/)를 참조해 주세요!)

## 시작하기 전에 : CPU는 어떻게 이루어져 있을까요?

컴퓨터의 CPU는 프로그램의 연산을 처리하고 시스템을 관리합니다. 현대의 CPU는 주파수가 4GHz(초당 40억회 연산)를 넘어섰죠. 하지만 CPU가 아무리 빨라도, 계산할 데이터들을 기억장치에서 가져오는 속도가 느리면 결국 기다려야 하므로 병목이 됩니다. 이 문제를 해결하기 위해 CPU 내부에는 여러 부품들이 데이터 저장 및 전송을 도와줍니다.

그렇다면 CPU 안에는 어떤 부품들이 있고, 각 부품들의 처리 속도는 얼마나 빠를까요?

|부품|기능|속도(클럭 사이클 시간)|
|---|------|---|
|산술논리장치(ALU)|CPU 내부에서 사칙연산, 논리연산 등 실제 연산을 수행하는 핵심 장치.|0.5 사이클|
|레지스터|ALU가 연산할 때 사용하는 극소량의 임시 기억 장치. (rax, rdi 등)|1 사이클|
|캐시 메모리(L1/L2/L3 Cache)|CPU 칩 내부에 존재하며, 자주 쓰는 데이터를 미리 저장해 놓은 초고속 창고.|4-75 사이클|
|주기억장치(RAM)|CPU와는 독립된 부품이자, 컴퓨터의 주 메모리. 커널과 프로세스가 실제로 적재되는 공간.|150-250 사이클|

> **클럭 사이클 시간(Clock Cycle Time)이란?**
>
> CPU를 포함한 디지털 회로에서 동기화/시간 신호인 클럭 신호가 1회 진동(주기, 사이클)을 완료하는데 걸리는 시간을 말합니다.
>
> 예를 들어, CPU의 주파수가 4GHz라면 클럭이 1초에 약 40억 번 진동합니다. 이 경우 클럭의 한 사이클이 도는 데 약 40억 분의 1초가 걸리며, 이것이 클럭 사이클 시간입니다.
>
> 프로그램이 CPU에서 실행되는 총 실행 시간(CPU Time)은 다음과 같이 예상합니다 : (명령어의 수)\*(명령어 당 평균 소요 클럭 사이클 수)\*(클럭 사이클 시간)
>
> 클럭 사이클 시간은 CPU 관점에서 작업별 실제 대기 비용을 직관적으로 보여줍니다.

살펴보면 RAM은 ALU에 비하면 매우 느립니다. ALU가 아무리 빨라도 RAM이 ALU에 정보를 전달하는 속도가 느리면 컴퓨터가 제 성능을 발휘하기 힘들겠죠? 이것을 보완하는 것이 레지스터인데, 레지스터는 속도는 가장 빠르지만 그 수가 한정되어 있고 한 번에 최대 8바이트 까지만 정보를 담을 수 있습니다. 다른 방법은 없을까요?

그래서 CPU는 추가적인 기억장치인 캐시 메모리를 사용합니다.

CPU가 RAM에서 데이터를 가지고 올 때, **나중에 또 사용할 가능성이 있는 주변 데이터들까지 같이 가지고 와서 CPU 칩 내부의 캐시 메모리 영역에 저장합니다.** 이후 같은 데이터가 또 필요하다면 캐시에서 데이터를 바로 가지고 오면 되므로, CPU는 엄청난 수준의 성능 향상을 이루었습니다.

**하지만 아이러니하게도... 바로 이 캐시 메모리와 CPU 성능 향상을 위한 노력이 역사상 최악의 보안 재난인 멜트다운의 원인이 되었습니다.** 어떻게 된 일일까요?

### 잠깐! 왜 캐시 메모리에는 찾고자 하는 데이터 주변에 있는 데이터들까지 같이 저장하나요?

컴퓨터에서 프로세스는 전체 주소 공간의 극히 일부 영역만 사용하며, 특정 순간에는 주소 공간 내에서 비교적 가장 작은 부분만 접근합니다. 이 성질을 지역성(locality)라 합니다.

지역성에는 다음과 같이 두 종류가 있습니다.

- 시간적(temporal) 지역성 : 한 번 참조된 항목은 곧바로 다시 참조되는 경향이 있다.
- 공간적(spatial) 지역성 : 어떤 항목이 참조되면 그 근처에 있는 다른 항목들도 곧바로 참조될 가능성이 높다.

따라서 CPU는 시간적 지역성을 보조하기 위해 캐시를 사용하며, 한 번에 여러 데이터를 같이 캐시에 저장함으로써 공간적 지역성을 보조합니다.

## CPU는 데이터를 어떻게 가져올까?

C 프로그래밍을 할 때 우리는 변수나 배열에서 아주 자연스럽게 값을 읽어옵니다. 이때 컴퓨터 내부, 즉 CPU에서는 정확히 어떤 일이 일어날까요?

아주 간단한 C 코드를 살펴봅시다.

```c
#include<stdio.h>
int main(void)
{
    int x = 3;
    int arr[6] = {1, 2, 3, 4, 5, 6};
    int y = arr[x]; // (*) 이 코드를 실행할 때 CPU 내부에서는 어떤 일이 벌어질까요?
    printf("%d\n", y);
    return 0;
}
```

`int y = arr[x];` 라는 코드 한 줄을 수행하려면 CPU는 내부적으로 다음과 같은 작업들을 순서대로 진행해야 합니다.

1. 변수 `x`의 값(3)을 읽어옵니다.
2. 배열 `arr`의 시작 주소를 찾고, 거기에 `x`를 더해 사용자가 원하는 메모리 위치를 계산한 뒤 실제 값을 가져옵니다.
3. 가져온 값(4)을 변수 `y`에 저장합니다.

과정만 보면 CPU가 이 작업들을 한 번에 하나씩, 순차적으로 실행하는 것처럼 보입니다. (실제로 아주 옛날의 초기 CPU들은 이렇게 순서대로만 일했습니다.)

**하지만! 현대의 CPU들은 성능 향상 및 작업 효율성을 위해 파이프라이닝(Pipelining)을 합니다.**

파이프라이닝을 사용하면 한 번에 여러 명령어를 동시에 실행할 수 있게 되며, 성능 최적화를 위해 **실행 흐름에서 뒤에 나오는 명령을 먼저 실행하는 비순차적 실행(Out-of-order Execution), 추측 실행(Speculative Execution) 등의 작업을 한답니다!**

- 비순차적 실행 : 현재 명령어를 실행하는 동안 뒤에 나오는 명령어들을 먼저 실행합니다.
- 추측 실행 : 실행 흐름에 조건문이 있으면 이 조건문을 참이라 가정하고 뒤에 나오는 명령을 먼저 실행합니다. 만약 조건문이 참이면 시간을 아낀 것이고, 거짓이면 했던 작업을 다시 원래대로 돌려 놓으면 됩니다.

이처럼 현대의 CPU들은 성능을 최대한 향상시키기 위해 이처럼 작업 순서를 뒤죽박죽 섞거나 미래도 예측하는 등 복잡한 작업들을 합니다.

참으로 똑똑하고 경이로운 기술이죠? **하지만 CPU의 이 성능 향상을 위한 특성이, 후술할 전 세계 정보보안을 뒤흔든 역사상 최악의 재난(멜트다운)을 일으키는 주범이 되고 맙니다.**

## 멜트다운 - 완벽해 보이던 CPU의 실수

멜트다운은 **CPU의 비순차적 실행의 동작 과정을 악용하여 커널 영역의 메모리에 기록된 값을 사용자 영역에서 읽을 수 있는 취약점**입니다.

이해를 돕기 위해 아래의 의사코드(Pseudo-code) 시나리오를 상상해 봅시다. 유저 영역의 해커 프로세스가 커널 영역의 비밀 데이터에 접근하려 하는 상황입니다.

```text
A : x = 해커가 몰래 읽고 싶은 커널 영역의 주소
B : y = [x] (메모리상에서 커널 주소 x에 위치한 실제 값을 가져옴)
C : y를 가지고 무언가를 한다.
```

정상적인 논리 흐름대로라면 A를 실행한 후, B를 실행하는 도중 권한 문제로 인해(SIGSEGV) 프로세스가 즉시 죽게 됩니다. 0장에서 배웠듯 사용자 영역은 커널 영역에 접근할 수 없기 때문이죠. 따라서 C에는 접근도 하지 못해야 정상입니다.

**하지만 여기서 CPU가 이 작업을 '비순차적 실행'을 해버린다면 어떻게 될까요?**

CPU는 B 작업을 진행하는 동안, 결과를 기다리는 대신 **몰래 읽어온 y를 사용해 C를 먼저 실행합니다.** 즉, 권한 검사가 끝나기도 전에 커널 메모리에 접근해서 그 안에 있는 값을 읽어 오고 다른 작업을 합니다!

### 잠깐! 그렇다면 CPU가 권한 검사가 끝났을 때 B, C를 모두 작업 이전으로 되돌려 놓으면 문제가 되지 않나요?

겉보기에는 작업을 먼저 하다가 권한 문제가 발생했으니, B, C 과정을 모두 실행 이전을 되돌려 놓고(롤백, Rollback) 프로세스를 죽입니다. 결과적으로 B, C의 연산 결과는 시스템에 반영되지 않았으므로 아무 문제가 없어 보입니다.

**그러나 이 과정에서 현대 CPU 설계자들이 매우 치명적인 실수를 하고 말았습니다.**

## 해커가 어떻게 값을 읽을 수 있는가?

비순차적 실행 때문에 권한이 없어도 커널 메모리를 읽는 코드가 '잠깐' 실행될 수 있음을 확인했습니다. 하지만 값은 레지스터에서 곧바로 지워져 버리죠. 그렇다면 해커는 도대체 어떻게 커널 내부의 데이터 y를 획득할 수 있을까요?

정답은 바로 **CPU의 캐시 메모리를 정보 유출용 비밀 통로(Covert Channel)로 악용하는 것입니다!**

해커가 캐시 메모리의 내부를 직접 들여다볼 수는 없지만, 캐시를 교묘하게 이용하면 값을 알아낼 수 있습니다. 아래의 의사코드 시나리오를 상상해 보세요.

```text
[주 실행 코드]
O : 길이가 256인 배열 arr[]을 준비하고, 캐시에서 모두 비워둔다.
A : x = 해커가 몰래 읽고 싶은 커널 영역의 주소
B : y = BYTE [x] (커널 주소 x에서 1바이트 크기의 비밀 값 y를 몰래 읽어옴. y는 0~255 중 하나)
C : arr[y] 에 접근한다. (비밀 값을 배열의 '인덱스'로 사용!)

-----------------------------------------------------------
[오류 처리 핸들러 - SIGSEGV 발생 시 프로세스가 죽는 대신 실행됨]
P : arr[0]부터 arr[255]까지 순차적으로 하나씩 접근하며 '접근하는 데 걸린 시간'을 측정한다.
Q : 남들에 비해 응답 시간이 압도적으로 짧은 인덱스(d)를 찾아낸다. 그 d가 바로 비밀 값 y이다!
```

이번에는 B 과정에서 커널 데이터를 단 1바이트(0x00~0xFF, 즉 0~255 사이의 값)만 읽어오고, C 과정에서 그 비밀 값을 배열의 인덱스로 사용하여 `arr[y]`에 접근하고 있습니다.

물론 B를 실행할 권한이 없으므로, 비순차적 실행으로 몰래 진행되었던 B와 C는 곧바로 발각되어 실행 이전으로 되돌려지고(Rollback) 프로세스에는 오류(SIGSEGV)가 발생합니다.

**하지만... CPU 설계자들은 레지스터만 초기화했을 뿐, 캐시 메모리를 청소하는 것은 깜빡했습니다!**

C가 아주 잠깐 실행되는 바람에, `arr[y]`의 데이터가 CPU의 캐시 메모리에 등록되었습니다. B와 C가 롤백되었어도, **캐시 메모리에는 arr[y]가 불려 왔었다는 '흔적'이 고스란히 남아 있습니다.** 이제 해커는 이 흔적을 찾아내기만 하면 됩니다.

### 값을 유출하는 순간은 이렇게!

캐시를 확인하기 위해, 해커는 오류(SIGSEGV)가 발생하더라도 프로그램이 죽지 않도록 사전에 **오류 처리 핸들러(Signal Handler)를 설정**해 두었습니다. 오류가 발생하면 자연스럽게 P 과정으로 넘어갑니다.

P 과정에서 해커는 arr[0]부터 arr[255]까지 256개의 인덱스를 하나씩 접근해보며 **데이터에 접근하는데 걸리는 시간(접근 속도)을 정밀하게 측정합니다.**

만약 커널의 비밀 값 y가 65였다고 가정해 봅시다. 256개의 주소 중 오직 arr\[65\]만이 캐시에 남아있는 상황에서 CPU는 다음과 같이 동작합니다.

- arr\[65\]에 접근할 때: 이 정보는 캐시에 있으므로 빠르게 접근합니다. (Cache Hit)
- 나머지 주소에 접근할 때: 캐시에 없으므로, 저 멀리 느린 RAM에 접근하느라 시간이 오래 걸립니다. (Cache Miss)

이렇게 되면, 해커는 arr\[65\]에 접근하는데 걸리는 시간이 다른 인덱스에 비해 월등히 짧음을 알 수 있습니다. 따라서 해커는 y = 65 임을 알 수 있습니다.
